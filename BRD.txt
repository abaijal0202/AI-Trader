



Technical Implementation Guide – Agentic AI Trading System (ICICI Breeze + Ollama + React Flow)


Executive Overview and Implementation Assumptions


Objective

This guide describes the production implementation of a compliance-first, local-first, fail-closed agentic trading system for Indian retail markets using:


ICICI Direct Breeze API for broker integration


Ollama for local LLM inference


FastAPI/Python for backend and orchestration


PostgreSQL + TimescaleDB for transactional and time-series storage


Redis for throttling, caching, pub/sub, and distributed coordination


React + React Flow for operator UI and agent visualization


Nginx for reverse proxy and TLS termination


Docker / Kubernetes for deployment


Prometheus / Grafana for monitoring


HashiCorp Vault for secret management





Architecture Principles





Compliance-first




Every execution path must enforce:


Registered static IP egress


Maximum 10 orders per second


Single API key for unregistered algo routing


Limit orders only in production policy


Full auditability of prompts, signals, approvals, and executions





Fail-closed




When any of the following fails, the system must default to no-trade:


Broker authentication


Static IP validation


Data staleness checks


Risk gateway decision


LLM schema validation


Margin validation


Market feed health





Local-first




Sensitive data must remain on controlled infrastructure:


Ollama runs locally or on private network only


No cloud LLM calls in production


Secrets stored in Vault


Internal service-to-service traffic restricted by network policy





Core Guardrails

Critical rule: LLM output must never directly trigger market execution.

Every proposed action must pass deterministic validation, risk checks, compliance filters, and explicit execution policy enforcement.





Key Assumptions

Because Breeze API details can vary by broker release and documentation version, the team must validate the following before go-live:


Exact request encoding semantics for GET-with-body behavior


Current WebSocket auth payload format and endpoint URL


Supported order types per segment


Sandbox vs production parity


Any newly introduced broker headers or checksum variations

Integration Constraints

From current Breeze documentation and BRD assumptions:


100 API calls/minute


5000 API calls/day


10 OPS combined across place/modify/cancel/square-off

Production Pattern

Use a dedicated Market Data Gateway service:


Maintains single upstream broker WebSocket sessions


Tracks subscriptions by instrument


Detects stale streams


Re-broadcasts normalized events to internal consumers and UI





Components





Upstream WS Client: broker connection


Subscription Registry: Redis set/hash of subscribed instruments


Feed Normalizer: maps raw ticks/order updates to internal schema


Stale Feed Monitor: detects no-tick gaps


Internal WS Hub: pushes events to React UI and backend services
